# 需求方案分析方法论（方案分析模式）

适用场景：写业务代码之前，把需求文档 / 用户 prompt 结合项目上下文，产出两份交付文档。

## 一、信息收集（先做足，再下笔）
1. 读需求文档原文，圈出**明确需求**、**隐含需求**、**未说明处**。
2. 读相关既有代码：分层结构、表结构、既有 API、既有约定（命名/异常/事务/权限）。
3. 收集上下文维度：
   - 功能：做什么、面向谁、主流程/分支/异常
   - 数据：新增/改动的表、字段、类型、索引、关系、数据迁移
   - 接口：新增/改动的 API、请求/响应契约、错误码、鉴权
   - 非功能：性能/并发、幂等、缓存、事务、兼容性、安全、日志监控

## 二、澄清（必须问，不许猜）
只要出现以下任一项，就用提问澄清，直到明确：
- 需求有歧义/多种理解
- 存在多种可行方案且影响大（选型需用户拍板）
- 关键字段/状态/规则缺失
- 与既有逻辑冲突
- 边界与异常处理规则未定义
- 验收标准不明确

> 宁可多问一轮，也不要基于假设产出方案。

## 三、方案设计
- 用项目既有的分层与模式，不引入陌生框架。
- 明确每个改动的原因（为什么这么做）与实现方式（怎么做）。
- 拆出风险点与规避措施（并发、数据一致性、兼容性、回滚、灰度）。

## 四、两份交付物
1. **用户方案文档**（简略、给用户看）：
   - 核心业务逻辑 | 新增/修改的表 | 新增/修改的 API | 关键流程
   - 语言平实，帮助用户快速恢复记忆。
2. **开发文档**（详细、供另一个 AI 写代码）：
   - 背景目标 / 方案选型理由 / 架构分层 / 模块逻辑与实现方式
   - 数据表 DDL 说明 / API 契约（入参出参状态码异常）/ 可能问题与规避
   - 测试要点 / 上线与迁移注意 / 明确假设

## 五、收尾
- 自查：方案是否覆盖所有已澄清的点？是否还有未决问题？
- 列出关键决策点，便于用户复核。
