# Java 后端开发方法论（代码开发模式）

适用场景：拿到《开发文档》或用户明确的开发 prompt 后，进行 Java 业务代码实现。

## 一、开工前（先对齐，再动手）
1. 通读《开发文档》与相关既有代码，确认项目约定：
   - 分层：controller / service / mapper / entity / vo / dto / config 等
   - 命名：包名、类名、方法名、参数、常量、枚举
   - 规范：异常体系、事务边界、缓存策略、日志约定、参数校验、统一返回结构
2. 明确开发粒度 —— 问清用户选择哪种：
   - **逐个开发**：一个方法 / 一个模块按顺序实现，每个完成即自检再继续。
   - **全量开发**：一次性写完所有业务代码，最后统一逐文件审查并修正。
   - 用户未指定时默认“全量开发最后统一审查”。

## 二、编写（互联网 Java 规范 + 行级注释）
1. 严格匹配项目既有实现方式，不引入项目中不存在的框架 / 依赖 / 模式。
2. 遵循互联网 Java 后端规范：
   - 分层清晰、职责单一；Controller 只做入参校验与出参包装，业务放 Service。
   - 命名见名知义；方法尽量短小、单一职责。
   - 事务只加在真正需要的地方（写操作 / 多步骤）；只读查询不加事务。
   - 参数校验前置；处理空指针、集合为空、除零等边界。
   - 合理使用缓存并处理一致性；注意幂等与并发（乐观锁 / 唯一索引 / 分布式锁按需）。
   - 异常：业务异常与系统异常区分，日志记录关键上下文，不吞异常。
3. 行级注释：每段逻辑都要有中文行级注释，重点是**为什么这么做**与**边界/注意点**，而不是复述代码本身。

## 三、自我审查（写完必查）
每个文件写完都自查：
- 命名 / 分层是否正确
- 是否覆盖所有边界与异常（空、非法输入、并发、数据不存在、幂等）
- 事务边界是否合理、是否有隐藏的 N+1 / 全表扫描
- 缓存 / 锁是否存在一致性问题
- 日志是否足够定位问题
- 是否超出《开发文档》范围做了“顺手优化”

## 四、测试与收尾
1. 开发文档范围内的【业务代码】全部完成并自检后，用 ask_user 向用户确认“业务代码已完成，是否开始写测试”。
2. 得到确认后才写测试：按项目既有测试框架与约定（JUnit / Mockito / Testcontainers / Spring Boot Test），只覆盖新增业务逻辑。
3. 全部完成总结：改动清单、测试结果、以及需要用户注意的点（如数据库变更、上线顺序、配置项）。
